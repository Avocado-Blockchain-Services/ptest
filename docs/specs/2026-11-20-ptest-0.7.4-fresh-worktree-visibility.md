# Spec: fresh-worktree speed, loud baseline refusals, coverage at push (ptest 0.7.4)

Date: 2026-11-20. Status: draft for user approval. The user asked for items 1
and 2 below, plus the coverage policy (G6) and the per-project config changes
(Rollout), and wants problems of this kind to be caught quickly from now on.

## Problem (observed in persea, 2026-11-20)

An agent ran a bare `ptest` in a newly created chain worktree of
`persea_content_maker_unified` after a commit that touched only
`web/.../agent-status-switch.tsx`. The run:

1. ran `uv sync --locked` as first-run setup, which installed
   `pytest-xdist==3.8.0`. pytest then loaded it (`plugins: xdist-3.8.0`), but
   the run ended with `parallel-workers: serial: pytest-xdist is not installed
   in the project environment yet`. ptest decides the worker count
   (`executability.parallel_request`, `operations.py` ~3438) and reserves slots
   before setup runs (`_run_guard`, ~3855). So 1,940 API tests ran on one
   worker, and the agent gave up before the end line.
2. printed `api · changed vs feature/campaign-followups: no changes → 1940
   tests` with `dynamic · 29 functions changed, 8 modules changed`. The diff
   was empty; the tests came from dynamic records. The output does not say
   what the "29 functions" were compared against, so neither the agent nor we
   could explain the run without another `ptest -v` run. **The cause of the
   1,940 is still unknown.** The history baseline does not feed dynamic
   selection, so a missing baseline alone does not explain it.
3. The previous full gate (f10ba742b, 18,548 API tests, green) ended with
   `no baseline recorded: gitignored files count as test inputs: .env (+1
   more)`. That one line, at the end of a long run, was the only sign. With no
   baseline, `--full` can never skip and other checkouts cannot reuse that
   green. Nothing reminded anyone later.
4. `ptest doctor --fix --offline --dry-run` on the main checkout reported
   `api: gitignored files not checked: input scan deadline exceeded` on one run
   and a complete scan on the next. On fullon2 `web` it reported `input
   fingerprint byte limit exceeded`. The check that should catch item 3 depends
   on timing.
5. Stale `__pycache__/*.pyc` files of deleted modules
   (`src/content_maker_api/hosted_mcp/__pycache__/…`) sit inside a declared
   input root. Python 3 never imports a `__pycache__` file without its source
   (PEP 3147), yet ptest treats such files as gitignored inputs, and
   `doctor --fix` drafts them one file at a time into `ignored_inputs`
   (observed in fullon2 launchpad/integrations, persea_ai control-plane, …).
6. The persea agent proposed fixing item 3 with `ignored_inputs = [".env"]`.
   ptest refuses that for a worktree's symlinked `.env`
   (`doctor_fix.py` ~1088); the right declaration is `non_input_outputs`. The
   agent could not learn this from the one-line refusal.

## Goals

G1. **Decide parallelism after setup.** When `parallel_request` falls back to
    serial for an *environment* reason (xdist or the pytest-cov/coverage pair
    is missing, duplicated, or unqualified), and setup is required for this run
    (`_required_setup_state` not None, no `--no-setup`), ptest runs setup first
    through the existing `run_setup_only` (exclusive admission, fingerprint
    recorded only on success), then calls `parallel_request` again and only
    then requests slots. Config reasons (`-n 1`, `--dist each`,
    `--maxprocesses`, `-n 0`) never trigger this. A grant is never resized.
    After the pre-run setup, the in-guard setup sees a current fingerprint and
    does nothing.

G2. **A refused baseline is loud on the gate.** When a passing `--full` run
    publishes no baseline, the end note keeps its reason and adds the cost and
    the fix in one line, e.g.
    `no baseline recorded: gitignored files count as test inputs: .env (+1
    more) · until fixed, --full always reruns and other checkouts cannot reuse
    this green · fix: ptest doctor --fix`. For `.env`-style paths and symlinks,
    the fix names `non_input_outputs`, never `ignored_inputs`.

G3. **The refusal stays visible afterwards.** The gate writes a refusal record
    (reason code, up to 3 paths, commit, time) into the project's
    `selection.db` kv, in the same transaction as the gate marker
    (`selection_engine._gate_marker`). All worktrees of the project share it.
    Every later bare, scoped, or `--full` run of that project prints one line
    `last gate at <sha12> (<age> ago) recorded no baseline: <reason> · fix:
    ptest doctor --fix` until a gate publishes a baseline, which deletes the
    record.

G4. **Dynamic selection names its reference.** The non-verbose `changed:` line
    of a dynamic plan says what the change was measured against, and names up
    to 3 of the changed modules: `… → 1940 tests (dynamic · 29 functions in 8
    modules changed since recorded runs, newest 3 d ago: content_maker_api.x,
    content_maker_api.y, +6 more · last gate <sha12> <age> ago)`. One run must
    be enough to tell "stale records" from "real change".

G5. **Orphan bytecode is never an input.** A `*.pyc`/`*.pyo` file whose path
    contains a `__pycache__` component counts neither for the input snapshot
    (`clean`), nor as an undeclared gitignored input, nor in doctor drafts.
    `doctor --fix` removes such entries from `ignored_inputs` (recognised by
    shape, like the 0.7.2 helper migration) and says how many it removed.

G6. **Doctor's gitignored check is deterministic and offline.** The
    undeclared-gitignored check lists names only (no content hashing), prunes
    `node_modules`, `.venv`, `__pycache__`, and every declared
    `non_input_outputs`/`ignored_inputs` entry before walking, and is bounded
    by an entry count, not a wall clock. The same tree gives the same answer on
    every run. If the bound is hit, doctor says so with the count. `ptest doctor
    --offline` reports undeclared gitignored inputs as an item (today only
    `--fix` mentions them as a comment).

G7. **Coverage only before pushing to origin** (user policy, 2026-11-20).
    - Iteration: bare `ptest` (unchanged).
    - End of a spec or chain, before merging into a local branch:
      `ptest --full` (no `--cov`).
    - Before pushing to origin: `ptest --full --cov`. On a tree whose
      `--full` is already green, this runs again, now with coverage (existing
      C9 behaviour, `operations.py` ~2872).
    - Update everywhere the gate is named: `COVERAGE_OWED` (`progress.py:203`)
      becomes `coverage gate still owed before pushing to origin: ptest --full
      --cov`. Also the repository agent guide and its copy `docs/ptest-agent.md`,
      `resources/agent-guide.md`, the skill templates in `agent_rules.py` (keep
      the current text in the previous-versions table so `ptest rules --apply`
      refreshes it), and README.
    - Stay within the guide's line-budget test.
    - The "exactly once per spec" wording becomes "once per spec before a local
      merge, once more before a push to origin".

### Open GitHub issues folded in (all still present on main 262a1a6)

G8. **#3: installer on macOS bash 3.2.** `install.sh:51` expands an empty
    `"${forwarded[@]}"` under `set -u`. Use `${forwarded[@]+"${forwarded[@]}"}`.
    Test: run `install.sh` with no extra arguments under `bash --posix`-style
    `set -u` and an empty array (a shell-level test that checks the expansion
    pattern, since CI has no bash 3.2). Also add a lint row that rejects a bare
    `"${…[@]}"` in `install.sh`/`get.sh`.

G9. **#4: macOS PID 0 in the process-group scans.** `guard.py:347`
    (`psutil.process_iter`) and `platform.py:493` (`psutil.pids`) both call
    `os.getpgid(0)`, which returns the *caller's* group, so the guard always
    sees a live member and ends exit 70. Skip `pid <= 0` in both loops (the
    same rule `platform.py:441` already applies to single-pid observation).
    Test: a fake process table that yields PID 0 whose `getpgid` returns the
    guard's group, so the scan reports "no live member". A Linux twin keeps
    today's result. Not live-verifiable here (no macOS machine); say so in the
    release notes.

G10. **#5: one large gitignored file aborts a full run (exit 70).** A
    gitignored file over `_MAX_FILE_BYTES` (16 MiB, `source.py:34`) raises
    `scan-limit` and the run ends incomplete without naming the file. Change:
    - an over-limit **gitignored** file never makes the run incomplete. It
      counts as an undeclared input (baseline refused through G2/G3), and the
      refusal names the file and its size.
    - `.mypy_cache` and `.ruff_cache` are non-inputs by default, since no test
      reads them.
    - Tracked files keep today's limit and behaviour.
    Test: issue #5's repro (a 17 MB `.mypy_cache/3.12/cache.db`) passes, and a
    17 MB undeclared `data/blob.bin` passes with the baseline refused and named.

## Non-goals

- Hashing gitignored inputs into the baseline instead of refusing it (a design
  question, separate spec).
- Reading other checkouts' last-green records, and a `--base` line in the
  skill. Neither caused this incident; they remain open ideas.
- A git pre-push hook that enforces G7. Guidance only in 0.7.4.
- Finding why persea selected 1,940 tests. G4 makes the next run say why.

## Abuse cases (negative twins)

Identity, authorization: N/A, a local CLI with no credentials or actors.
Tenancy maps to project isolation:

| # | Must not happen | Test |
|---|---|---|
| A1 | The text of `.env` or any gitignored file appears in output, kv, or result JSON: paths only | `test_baseline_refusal_prints_paths_never_content` |
| A2 | A path with terminal escapes, or `../`, written into the kv by a tampered `selection.db`, reaches the terminal unescaped | `test_refusal_record_paths_are_validated_and_escaped` (hostile-input table: escape bytes, traversal, absolute, oversized, >3 paths) |
| A3 | An unreadable, malformed, or future-version refusal record crashes a run or changes selection | `test_malformed_refusal_record_is_ignored` |
| A4 | A refusal of project A shows on project B in the same monorepo | `test_refusal_record_is_per_project` |
| A5 | A stale refusal survives a later gate that published a baseline | `test_published_baseline_clears_refusal` |
| A6 | Pre-run setup runs twice when two first runs start at once in one checkout | `test_concurrent_first_runs_set_up_once` |
| A7 | Cancel during the pre-run setup leaves a setup fingerprint, a held slot, or a non-130 exit | `test_cancel_during_presetup_records_nothing` |
| A8 | Setup installs an unqualified or duplicate xdist and ptest runs parallel anyway | `test_presetup_unqualified_xdist_stays_serial_with_reason` |
| A9 | `--no-setup`, or a config reason (`-n 1`, `--dist each`), triggers a pre-run setup | `test_config_reasons_never_presetup` |
| A10 | A failed pre-run setup runs the tests anyway | `test_presetup_failure_ends_with_setup_failed` |

## Tests (oracle per row)

- G1 (oracle: incident item 1). Fake project whose setup creates the
  `pytest_xdist-<qualified>.dist-info` directory, so the first run requests
  `max_slots`, not 1, and the end line has no `serial:` reason. A twin with
  `--no-setup` stays serial with today's text. Same for the cov pair under
  `--cov`. Rewrite the pinned rows in `tests/ng/test_executability.py`
  (1264–1272, 1406, 1420–1424) and
  `tests/ng/test_deterministic_items.py` (~690) to the new wording, without
  dropping a row.
- G2/G3 (oracle: incident item 3). Gate with an undeclared ignored `.env`: end
  line carries cost and fix. A later bare run in a *second* worktree of the same
  project prints the `last gate … recorded no baseline` line. Declare `.env`,
  rerun the gate, and the line is gone. Extend
  `tests/ng/test_changed_explain.py:280–335`.
- G4 (oracle: incident item 2). Empty diff plus records older than a source
  change: the line names the reference, newest record age, up to 3 modules
  and `+N more`, and the gate sha.
- G5 (oracle: incident item 5, PEP 3147). Orphan `__pycache__/x.cpython-313.pyc`
  inside an input root: the snapshot stays clean, the baseline is published,
  and doctor drafts nothing. Plus A11, A12.
- G6 (oracle: incident item 4). The same fixture tree scanned twice under an
  injected slow clock gives the same result. A tree with a huge
  `node_modules` finishes without "deadline exceeded". `doctor --offline`
  lists the undeclared file as an item.
- G7 (oracle: user policy). Guidance snapshot tests and the line-budget test
  updated. `COVERAGE_OWED` text pinned. `ptest rules --apply` on a 0.7.3
  skill rewrites it.

Every test is bounded (no sleeps for synchronisation, fake clocks, tmp trees);
none runs a real `uv sync` or a network call.

## Gates

Secrets: gitleaks over the diff (A1 makes output paths-only). SAST: the
repo's existing lint/type checks. Dependencies: no new ones. Property: G5's
path rule gets a hypothesis test over generated relative paths (a
`__pycache__` component plus a `.pyc`/`.pyo` suffix gives no input; anything
else is unchanged). Completion: one `ptest --full` before merging to local
main; `ptest --full --cov` before the push (per G7).

## Rollout (done 2026-11-20, local commits, not pushed)

`.env`-style files were declared in `[selection] non_input_outputs`:
persea_content_maker_unified `api`, `web` (7496fecbd, dev);
fullon2_integrated `api`, `launchpad`, `server` (ff349c60, dev);
checador (5687731); money_maker (9b24e09); cuentas_avocado (64e23ba).
legacy_fullon2/fullon2 was edited, but its `.ptest.toml` was never committed,
so it was left uncommitted. `.ptest.toml` is a full trigger, so the next run in
each of those projects runs its full suite once. Worktrees created before
these commits keep the old config until they merge the base branch.

What this does and does not fix:
- It restores the baseline when a gate runs in a worktree, which brings back
  `--full` skips and reuse across checkouts.
- It does not explain or stop the 1,940-test over-selection; G4 is what will
  diagnose that.
- In the persea chain worktree (`feature/campaign-followups`), the only
  undeclared ignored file was the `.env` symlink. The gate's "+1 more" no
  longer exists there, so it cannot be identified.
- **Main checkouts still have undeclared leftovers**, so a gate run in a main
  checkout would still record no baseline:
  - persea api `build`, `logs`, and the orphan `hosted_mcp`/`mcp_oauth` dirs
  - persea web `.certs`, `.firebase`, `dist`, `tsconfig.node.tsbuildinfo`
  - stale `__pycache__` files in fullon2 server/launchpad/integrations and
    persea_ai.
- G5 removes the bytecode cases. The rest are build outputs to delete or
  declare per project, after G6 makes doctor's list reliable.
