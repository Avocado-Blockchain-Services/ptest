# pipeline — ptest test-policy (worktree slug: test-policy). Three parts, one repo, base branch main.

PRINCIPLE: docs/ptest-agent.md is @-included into every agent session of every ptest user (CLAUDE.md managed block is `@docs/ptest-agent.md`), so every line there costs every session. Keep it tight; put detail in on-demand `ptest guide` content. Never write a numeric target that no tool in ptest can measure.

A. TIER 1, ships to every user through the existing hash-tracked guide refresh:
1. src/ptest/resources/repository-agent-guide.md: add a short `## Writing tests` section (about 6 lines, not a long checklist): every test names its oracle (spec clause, bug report, deliberately pinned behaviour, or invariant) and a test whose expected value was read off the implementation should not be written; a bug fix starts with a failing repro test; never add tests only to raise coverage, and keep the project's existing coverage gate as it is; where input crosses a trust boundary use one table-driven hostile-input test with only the rows that apply (empty/oversized, traversal/injection, wrong owner, unauthenticated); point to `ptest guide tests` for the full checklist. Respect the existing guide line cap (tests assert it); if the cap must move, move it only by the lines added and say so in the design.
2. src/ptest/resources/agent-guide.md: reword "Preserve assertions, test inventory, coverage, and test semantics" so it says preserve assertions, test inventory, test semantics and the existing coverage gate, and never add tests only to raise coverage. Keep meaning otherwise.
3. Add the current (pre-change) repository-agent-guide.md sha256 to _PREVIOUS_GUIDE_SHA256S in src/ptest/agent_rules.py so existing installs refresh via `ptest rules --apply` / init refresh. Same for any other managed text whose bytes change.
4. New recipe src/ptest/resources/recipes/tests.md registered in checklist.py _RECIPE_FILES as "tests", rendered by `ptest guide` like the other recipes: the full checklist (oracle question; anti-patterns: mock-echo asserting only that a call happened, expected values copied from the implementation, unreviewed snapshots, assertion-less tests, tests of private functions, import-only tests; test budget: one behaviour test per requirement, one repro per bug, one hostile-input table per trust boundary with applicable rows only, one role x action authz matrix per service with authz; coverage: a gate is a floor not a target; fix a failing gate by testing behaviour or deleting dead code, never with assertion-free tests), with a short pytest parametrize example and a vitest test.each example.
5. evals/agent-usage/scenarios.toml: add two scenarios (and whatever scorer/fixture wiring scripts/agent_eval.py needs): (a) asked to fix a reported bug, the expected answer writes a failing repro test first; (b) project gate is 85% and coverage is 84%, the expected answer does not add padding tests and instead tests real untested behaviour or reports it.

B. DOCTOR, read-only and offline (static, sends nothing, writes nothing): a plain-words "Test policy" section in `ptest doctor` / `ptest doctor --offline` human output and recommendations.md, per project: where a coverage gate is configured (coverage.py fail_under in pyproject.toml [tool.coverage.report], .coveragerc, setup.cfg/tox.ini [coverage:report]; pytest-cov --cov-fail-under in [runner] args/full_args or pytest addopts); line vs branch (coverage.py branch / --cov-branch); omit patterns and the count of `pragma: no cover` lines under the project's source; and lines in AGENTS.md/CLAUDE.md/GEMINI.md outside ptest managed blocks that state a coverage percentage. Name the risks in plain words (e.g. a global line-only percentage rewards touching lines, not checking behaviour; omit lists hide code from the number) and print a copyable suggestion (keep the existing gate as a floor and do not raise it by adding tests; consider branch coverage; fix conflicting instruction lines yourself). Vitest/Vite configs are executable code: report `vitest coverage thresholds: not inspected (config is code)`, never regex-parse them. Never edit coverage config or instruction files. Never mark anything ready; no readiness row turns green from this. Doctor --json must stay byte-compatible with the frozen v1 schema (docs/schemas/v1/doctor.json): put the new facts only in human output and recommendations.md unless the schema already has a place for them. No measured coverage rate in this run (ptest persists none; reading stale project report files is out of scope).

C. OPT-IN POLICY, only with user consent: a static, ptest-owned file docs/ptest-test-policy.md holding the stricter stance (the test budget; do not add a test without a named oracle; the coverage gate is a floor, not a target; do not add tests to raise coverage), installed only on explicit acceptance: an interactive y/N prompt in `ptest init` (alongside the existing agents prompt) and an explicit flag (e.g. `ptest init --test-policy` / `ptest rules --apply --test-policy`; pick the grammar in the design consistent with existing flags). Non-interactive runs (agents, CI, pipes) without the flag never install it. When installed, the EXISTING managed block in AGENTS.md/CLAUDE.md/GEMINI.md gains one reference line to it (no second marker system, no precedence clause); both block variants must be recognised by apply, refresh, worktree checks (worktree.py AGENT_RULE_FILES) and `ptest uninstall`, which must remove the policy file and restore the block. The policy file is hash-tracked like docs/ptest-agent.md so later ptest versions refresh it and a user-edited copy is never overwritten. Before writing, show exactly which files change (and --dry-run shows the same without writing). Conflicting coverage-percent lines in the user's instruction files are listed for the user to edit; ptest never edits user-written lines. No numbers in the policy file. init --json output stays byte-compatible with docs/schemas/v1/init.json.

USER-FACING TEXT: plain words; do not cite any external benchmark or eval as evidence.

OUT OF SCOPE (later specs): measured coverage rate, diff/changed-line coverage, mutation checks, assertion-less test detection, fail-first against base, editing user lines.
